Migrate to supervisor mode

Companion mode is the compatibility path for servers that predate the agent. Migrating retires the game image, the companion agent, and — once no companions remain — the docker socket proxy. The world survives because everything lives in the dataset: the game install, saves and config never move. Expect one restart's worth of downtime.

What you end up with: one supervisor-mode container per server that installs, runs and restarts the game itself — real exit codes, crash backoff, game logs in the dashboard, and no docker proxy needed for that server.

The migration, step by step

  1. Safety net. Run a backup from the dashboard, and snapshot the server's dataset.
  2. Stop the old server. Stop from the server card (the usual save-then-shutdown sequence runs), then stop and delete the old game container's app. Keep the dataset.
  3. Clear the container name on the server's edit form — it names the old game container, which stops existing in the next step, and docker-side features would point at a ghost. (The watchdog needs no attention: on a supervised server it stands down automatically, since the supervisor owns crash recovery.)
  4. Swap the stacks. Remove the companion agent service from wherever it lives, and deploy a supervisor-mode stack for the server:
    palworld-main/docker-compose.yml — the agent IS the server
    services:
  palagent:
    image: ghcr.io/safwyls/palagent:latest
    environment:
      - PALAGENT_TOKEN=${PALAGENT_TOKEN}          # reuse the companion's token
      - PALAGENT_MODE=supervisor
      - PALAGENT_ADMIN_PASSWORD=${PALWORLD_ADMIN_PASSWORD}  # the row's REST/RCON password
    volumes: ["./palworld:/palworld"]       # same path the game used before
    ports:
      - "8211:8211/udp"   # the ports the old app published
      - "8212:8212"
      - "25575:25575"
    networks: [default, palcon-net]
    restart: unless-stopped
networks:
  palcon-net:
    external: true
    Three details matter: the same volume path the old game container used; no SaveGames :ro overlay (unlike a companion, the game writes its own saves through this mount); and deploy it as its own stack, not inside Palcon's — the agent is the game server now, and a compose down on the dashboard must never be able to take it along. Reusing the companion's token saves a form edit.
  5. Update the server row if ports or the agent URL changed — a standalone stack publishes the agent port instead of sharing Palcon's network.
  6. Start from the card. The existing PalWorldSettings.ini is kept as-is; the management interfaces (REST/RCON) are enforced on every start, so the dashboard connects on its own. Verify the card shows palagent · supervisor and players can join.

A supervised server always answers to the agent first. Power buttons, scheduled restarts and update jobs all ask the agent before considering docker, so a leftover container name can't fight the supervisor over restarts — it just leaves docker-side extras (container logs, the stale-name cleanup above) pointing at a container that no longer exists. Servers deployed by the provisioner record their container name on purpose: there it names the supervisor's own container, which powers the log viewer and the optional container destroy on removal.

Rollback

If anything misbehaves: stop the supervisor stack, redeploy the old game app and companion agent, restore the watchdog/container-name settings — the dataset was never modified structurally, so the world is exactly where you left it.

After the last companion

Once every server is supervised, nothing uses the docker socket proxy anymore — remove the docker-proxy service and the DOCKER_HOST variable from Palcon's own stack. Power for every server now flows through its agent.
