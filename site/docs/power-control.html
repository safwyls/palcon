Power control

Palcon does not need, and should not be given, the host's Docker socket. That socket is root-equivalent — anything holding it can start a privileged container and take over the host.

The scoped proxy

Instead, docker-socket-proxy sits in front with only CONTAINERS=1 and POST=1, so Palcon gets exactly "inspect, start, stop, restart" and nothing else: no creating containers, no mounting volumes, no exec. The worst case if Palcon is compromised is a bounced game server. The deploy spec includes the proxy service; point DOCKER_HOST at it.

Set each server's Container name in its edit dialog to enable the controls; servers without one simply don't show them. Servers managed by a supervisor-mode palagent don't need any of this — power routes through the agent natively.

How stopping works

  1. Save the world, so nothing is lost regardless of what follows.
  2. Ask the game to shut itself down (a one-second in-game countdown), so the process exits normally with code 0 instead of being SIGKILLed.
  3. docker stop, which observes that clean exit inside its grace window — so a restart: unless-stopped policy treats it as an intentional stop rather than a crash to revive.

Each step is best-effort. A server that's already unresponsive can't save or shut itself down, and neither blocks stopping the container — which is often exactly why you're reaching for the button.

Why TrueNAS sometimes says "crashed". Palworld server images generally ignore SIGTERM, so a plain docker stop ends in SIGKILL and exit code 137 — which Docker and TrueNAS label "crashed". The save-then-ask sequence above avoids that. If you still see 137, the game was already unresponsive and was stopped by force, which in that situation is accurate.
