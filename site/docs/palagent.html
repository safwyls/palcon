palagent sidecar

Everything Palcon does beyond REST/RCON normally assumes it shares a filesystem and Docker host with the game server. palagent inverts that: a small trusted container sits next to each game server, holding the mounts and the SteamCMD tooling, and Palcon becomes a pure control plane speaking HTTP to it. That also makes remote game hosts possible.

Shape

  • One agent per game server — its own volume, auth token and compose stack. Blast radius stays per-server by construction.
  • Fixed verbs, not an exec agent. The agent exposes only dashboard-shaped operations. A leaked token can bounce or repair one game server and touch its files — nothing else.
  • Same repo, second image — ghcr.io/safwyls/palagent, sharing the same tag scheme as Palcon.

Companion mode

Your existing game image keeps running the server; the agent mounts the same volume and absorbs the file-side features: SteamCMD cache repair and validated updates, the save bundle, and atomic PalWorldSettings.ini writes. Save data stays kernel-enforced read-only inside the agent via a nested :ro bind. Container power stays with the docker proxy in this mode.

palworld-main/docker-compose.yml — game stack + companion
services:
  palworld:
    image: thijsvanloef/palworld-server-docker:latest
    volumes: ["./palworld:/palworld"]
    # ... existing game config unchanged ...
  palagent:
    image: ghcr.io/safwyls/palagent:latest
    volumes:
      - ./palworld:/palworld
      # saves stay mount-guaranteed read-only inside the agent
      - ./palworld/Pal/Saved/SaveGames:/palworld/Pal/Saved/SaveGames:ro
    environment:
      - PALAGENT_TOKEN=${PALAGENT_TOKEN}   # generated in the palcon UI
    networks: [palcon-net]
networks:
  palcon-net:
    external: true

Supervisor mode

PALAGENT_MODE=supervisor makes the agent be the server container: it installs the game via SteamCMD on first boot and runs PalServer.sh as a child process. Start/stop/restart, crash auto-restart with backoff, real exit codes and the game's stdout all become agent verbs — no game image, no docker proxy. Palcon routes power, status and logs to the agent automatically, and management interfaces (REST/RCON) are enforced into PalWorldSettings.ini before every start.

palworld-main/docker-compose.yml — the agent IS the server
services:
  palagent:
    image: ghcr.io/safwyls/palagent:latest
    environment:
      - PALAGENT_TOKEN=${PALAGENT_TOKEN}
      - PALAGENT_MODE=supervisor
      - PALAGENT_ADMIN_PASSWORD=${PALWORLD_ADMIN_PASSWORD}
    volumes: ["./palworld:/palworld"]   # the game writes its own saves
    ports:
      - "8211:8211/udp"   # game
      - "8212:8212"       # REST — for palcon
      - "25575:25575"     # RCON
    networks: [default, palcon-net]
    restart: unless-stopped

Deploy each game server as its own stack, never inside Palcon's — a docker compose down on the dashboard must be structurally unable to take a game server with it. The New server wizard generates these stack files for you. Running a companion today? The migration guide walks through the switch; the full design doc covers the API surface and lifecycle details.

One-click provisioning

Palcon itself never gains Docker create rights. The optional provisioner-mode agent (PALAGENT_MODE=provisioner) holds them instead, exposing a few locked verbs: instantiate the Palworld supervisor template, discover and adopt existing agent containers, and destroy what it created. The template lives in code — no arbitrary images, mounts or privileges are expressible. With PROVISIONER_URL/PROVISIONER_TOKEN set, the wizard deploys new servers in one click and can discover and re-adopt existing agent containers on the host, secrets recovered automatically.

Destroy is create's inverse and the only verb that unmakes anything: it refuses any container the same provisioner didn't create, stops the game gracefully so the world flushes, and never touches the data directory — the world lives in a host bind mount and survives. In Palcon it's an explicit opt-in on the remove-server dialog; removing a server still defaults to dropping just the row. Reclaiming the disk afterwards is a deliberate trip to the host, on purpose.

Understand the risk before deploying the provisioner. It holds the Docker socket as root, and a container holding the socket as root is root on the host. Its API is bounded by design — a hostile caller with the token can stamp out template containers and destroy the ones the provisioner made, but can't touch other containers, delete world data, or reach host root — yet bugs in those few handlers and supply-chain compromise of this repo's image are real exposure. Never publish its port; reach it over the compose network only. If in doubt: keep it stopped and start it only while provisioning — Palcon degrades gracefully to the paste flow — or don't deploy it at all. The full design doc spells out the three attack paths.

Auth

Each agent gets its own bearer token, generated in the Palcon UI, stored encrypted exactly like RCON/REST passwords, and pasted into the agent's environment. The agent refuses to start with a token under 16 characters.
